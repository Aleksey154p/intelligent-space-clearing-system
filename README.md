# Intelligent Space Clearing System v0.1

# Система интеллектуального освобождения ячеек склада для водителей погрузчиков.


![Матрица сложности](no_git/images/img.png)

**Проблема:** водитель не знает куда везти остаток из ячейки - слезает, осматривает соседние ячейки, ищет место, часто ошибается. Холостые пробеги, потеря времени.

**Решение:** водитель выбирает диапазон ячеек для освобождения - система анализирует склад и выдаёт оптимальный пошаговый маршрут. Что взять, куда везти, в какой последовательности.

## Матрица сложности

Склад разбит на 4 блока. Сложность маршрута зависит от того между какими блоками выполняется перемещение:

```
Блок A: P100–P110    Блок B: P111–P120
Блок C: P200–P210    Блок D: P211–P220
```

Формула: `сложность × количество ЕО = очки`

Алгоритм выбирает маршрут с минимальными очками.



## Правила алгоритма

- Целевая ячейка ищется по всему складу — не только внутри диапазона
- В целевую ячейку можно ставить только тот же продукт, что стоит в ней, если она не пустая
- Заблокированные ячейки исключаются (пока что)
- Выбирается маршрут с минимальной суммой очков сложности

## Что будет дорабатываться

**Алгоритм**
- Алгоритм - на данный момент работает с одним рядом Р100 - Р120 ячеек, вместимостью 21 ЕО, 7 видов продукции, каждую раз разная вариация наполненности виртуального склада, каждая итерация, разные входные данные о наполненности, на выходе всегда, самый выгодный по очкам сложности план перемещения ЕО с целью освободить штабель.  
![img.png](no_git/images/img_2.png)

**Многошаговый маршрут**
- На начальном этапе разработки, прототип системы строит маршрут из одного перемещения: взял из A, отвёз в B. В реальности этого часто недостаточно. Целевая ячейка может быть заполнена на 90% - туда влезет только часть паллетов. Тогда нужно сначала частично освободить целевую, потом везти основной остаток. Алгоритм должен просчитывать такие цепочки автоматически и выдавать полный многошаговый план за один запрос.

**Групповая оптимизация**
- Сейчас система освобождает одну ячейку диапазона. Но не стоит упускать возможность освободить несколько ячеек сразу, при не высоком показателе сложности, допускается вариативность предложенных планов работ, например освободить один штабель.вместимость_21 = 60 очков сложности, освободить 2 штабеля.вместимость_21_21 = 83 очка сложности

**Освобождение к месту отгрузки**
- Когда машина стоит на воротах DA07 и ждёт паллеты, каждая лишняя минута влияет на объем работ/человеко часы. Система должна уметь работать в режиме отгрузки: получить от SAP  обновление о резервации ЕО, найти их на складе и выстроить оптимальный маршрут доставки напрямую к месту отгрузки, если сложность отгрузки этого штабеля к воротам соответствует фавориту на место самого эффективного решения. Возможно имеет место быть создать промежуточные ячейки между непосредственно отгрузкой и ячейкой склада, ячейка в складе Pxxx, отгрузка DAxx, Rxx, допускаю вариант PDAxx, PRxx, во избежании беспорядка на складе, допускается перемещение в PDAxx, PRxx, только если карщик начал отгрузку транспорта, "заранее", "это точно будет грузиться" не допускается

**Учёт зарезервированных паллетов во время выполнения плана**
- Во время выполнения плана по освобождению места, штабель который освобождает карщик может стать зарезервированным для отгрузки, подобное обновление будет отслеживать фоновый агент, который при изменении статуса резервации, должен дать команду для алгоритма сразу же сделать пересчет, с учетом выполненной работы, если ячейка потеряла лидерство по очкам сложности, например ячейка далеко от места отгрузки, будет предложено освобождать другую ячейку, чтобы не терять время на проделанную работу, карщик может принять решение осуществить помощь с отгрузкой 

**Вариативность планов**
- Оптимальный по очкам маршрут не всегда оптимальный физически. Узкий проезд, низкий потолок, скользкий пол, ремонт - водитель знает склад лучше любого алгоритма. Система будет предлагать от 3 до 5 вариантов по возрастанию сложности (например 34 → 41 → 56 очков) с кратким описанием каждого. Водитель выбирает тот который выполнимее в текущих условиях.

**Надёжность**
- Пока что не представляю как это сделать без привязки сессии каждого терминала на котором осуществляется работа освобождения места с помощью ISCS ->

**Конкурентный доступ**
- На складе работают несколько погрузчиков одновременно. Два водителя могут выбрать один диапазон и начать работать с одной ячейкой. Без блокировки они будут мешать друг другу и получат некорректные планы. Решение - ячейка блокируется в момент когда водитель начинает выполнять план. Другой водитель видит её как занятую и получает альтернативный маршрут. После завершения или отмены - ячейка освобождается автоматически.

**Автообновление плана**
- Между моментом когда план был составлен и моментом когда водитель начал его выполнять, ситуация на складе могла измениться. Другой водитель уже переместил паллеты которые участвуют в плане. Система должна отслеживать состояние ячеек задействованных в активных планах и автоматически пересчитывать маршрут если что-то изменилось - до того как водитель обнаружит это физически.

**Устаревание плана**
- План составлен в 14:00, водитель отвлёкся, вернулся в 14:30. За это время склад мог существенно измениться. Система будет помечать план как устаревший через настраиваемый интервал (например 5 минут) и предложить пересчитать, не вижу тактической необходимости, пересчитывать весь склад за кадром без явной команды. Фоновому мониторингу должны подлежать только ячейки и ЕО которые участвуют в плане

**Управление**

**Динамическая матрица сложности**
- Сейчас значения сложности прописаны в коде. На реальном складе их нужно менять без участия разработчика. Ответственное лицо через интерфейс выставляет значения, согласовывает с водителями которые знают физику склада, и сохраняет. Любое изменение логируется - видно кто, когда и какие значения изменил. Это важно для калибровки алгоритма по результатам работы на реальном складе.

**Управление статусом ячеек**
- Ячейки закрываются по разным причинам: брак, авария, ремонт стеллажа. Об этом легко забыть - ячейка висит закрытой месяцами и система её не использует, теряя полезные паллето-места. Интерфейс управления решает это: открыть/закрыть ячейку с обязательным указанием причины и ответственного, журнал всех изменений, автоматические уведомления отвественному лицу о ячейках закрытых более N дней, недель, параметр настраиваемый

**Масштабирование**

**Поддержка полного склада**
- Текущий прототип работает с двумя рядами и четыремя зонами (Ячейки с Р100 до Р120, один ряд поделен на две половины A, B, для более точного определения сложности, поездка из Р101 в Р103, не равно поездке из Р101 в Р119, ряд с Р200 до Р220 сделан аналогично). Реальный склад значительно больше. Архитектура системы спроектирована так чтобы добавление новых зон требовало только обновления матрицы сложности - без переписывания алгоритма.

**Асинхронный анализ**
- При росте склада до 300+ ячеек и 5000+ паллетов последовательный перебор всех кандидатов начнёт занимать заметное время. Асинхронная обработка позволит анализировать несколько зон параллельно и выдавать результат значительно быстрее. Для водителя с погрузчиком разница между 0.1 секунды и 5 секундами ожидания существенна.

**Интеграция с SAP режим 2.2-3030**
- Сейчас водитель получает план на экране, фотографирует и выполняет вручную. Полная интеграция позволит системе напрямую создавать задания на перемещение в SAP. Водитель подтверждает план одной кнопкой - и задание уже в системе. Это исключает ошибки при ручном вводе и ускоряет работу.

**Мультизаводность***
- Речь может быть о новом стандарте отрасли, каждый завод имеет свою физику склада, свои ряды, свои сложности того или иного вида выполнения работ, но все производства где хранение осуществляется штабелями, адресным хранением и есть нехватка свободного места объединяет кое-что, это дальность поездки=сложность для обработки одной еденицы продукции складом. Общая платформа с локальными матрицами под каждое производство которое имеет свойства и проблемы описанные выше, позволит масштабировать это решение в отрасль. Без звездочки я не смог обойтись
